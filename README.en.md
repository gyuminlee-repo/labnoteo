# Labnote Assistant for Obsidian (labnoteo)

**Version 0.113.0**

[한국어](README.md)

A Markdown-based lab notebook for Obsidian for synthetic biology experiments on a biofoundry, with sample tracking, workflow checklists, unit operations, and optional LLM assistance.

This repository is the Obsidian port of the Labnote Assistant. It shares its platform-neutral parsing and domain logic with a companion VS Code extension, but is fully self-contained here.

To see the features first, the **[help site](https://sblabkribb.github.io/labnoteo/en/)** has a short clip of each one (Korean and English). To print worksheets, write on them, and file photos or scans of them back into notes, see the **[printout scan guide](docs/SCAN.md)** (Korean).

## Features

- **Sample tracking**: A dedicated Samples sidebar view. Define, insert, and edit samples (DNA, RNA, Plasmid, and custom types) — including a sidebar search box and a **storage-location** field — and move them between local (note) and global scope. You can also **right-click in a note and choose *Add sample*** to create one and insert its reference. Editing an alias lists the notes that still show the old one and offers to update them too. *View usages* on a sample's right-click menu lists the notes that use it and opens the one you pick (the MCP `get_sample` returns the same list as `usages`). A sample registered under the wrong type is fixed with *Change type* (Samples sidebar right-click or the definition window): its ID takes the new type's prefix, and the notes that use it are rewritten after asking. Without the mouse, the palette command *Open sample definition* opens the definition window for the sample under the cursor, or one picked by search, to edit, move, delete, or change its type. Aliases cannot contain `;` or `:` (they separate the ID, alias, and description in a note) or `#`, `[[`, `]]`, `*`, `_`, `` ` `` (Markdown reads them as a tag, link, emphasis, or code; `_` next to Korean turns italic), and descriptions cannot contain `;`. A used-up sample can stay registered with *Mark as discarded* on its Samples-view right-click menu; it then shows dimmed with `(discarded)` in the Samples view and autocomplete and sinks to the bottom of the suggestions (*Edit sample* keeps the mark, and the sample definition popup shows the discarded date). The palette command *Insert sample list of this experiment* inserts a Markdown table of this experiment's Local samples and the Global samples the note refers to, with ID, alias, description, location, scope, and discarded columns. Autocomplete's *Search catalog* appears only when a product catalog (`{Type}_*.json`) exists. In a lab note (`.labnote.md`), a sample ID that is in no registry (Local, Global, or a product catalog) and is not defined in the note itself gets a red wavy underline and a "Not in the sample registry" tooltip (in editing and reading view; nothing is marked while a registry JSON cannot be read). Dates in `#### Meta` are picked from the 📅 icon at the end of the line or by clicking the value (in a popout window too, where the picker opens in that window). When `End_date` ends up earlier than the block's `Start_date`, closing the picker says so, and one Ctrl+Z undoes a value set with the picker.
- **Workflow checklists**: A Workflows sidebar view to create and manage numbered workflow notes and keep the table of contents in sync. Its **Experiments** section at the top lists the vault's experiments grouped by status as `001 · title (2/5)` (number · title, workflows done/total); click one to open its README, or right-click → *Change experiment status* to change that experiment's status directly. The tooltip shows the title, folder, status, project (`project`), last update, and discussion flag. A group whose `status` is not an allowed value (e.g. `Failed`) is tagged `(not an allowed status)`. The **Search experiments** box above it filters experiments by folder name, title, project, and status (every word typed must match), and the switch next to it groups them **By status** or **By project** (experiments whose README `project` is the same, those without one under `(no project)`); the choice is saved. Both the Workflows and Samples views work from the keyboard: opened by command or ribbon, focus goes into the list; ↑↓ move, →← expand and collapse, Enter opens, and Shift+F10 or the menu key opens the right-click menu. Under a Korean UI, catalog tooltips show the Korean description.
- **Unit operations**: Insert hardware/software unit operations from a bundled catalog, with automatic heading normalization and TOC updates.
- **Sample suggestions & CSV export**: Inline suggestions and highlighting for sample references while editing, plus CSV export of note tables (Excel-compatible UTF-8 with BOM). Each suggestion shows its scope, such as `Local DNA sample` or `Global DNA sample`, and creating a sample whose alias the same experiment or the Global samples already use tells you so.
- **Experiment status, discussion flag, issue markers**: Track each experiment's lifecycle (`planned` → `in-progress` → … → `completed`/`failed`) in frontmatter, and flag a note for team discussion either whole (*Toggle discussion flag*) or at a specific line (`@issue;<ID>;<topic>` marker). The next push opens a GitHub Issue.
- **Note IDs, QR worksheets, scan filing (desktop)**: Every lab note gets a unique ID (`labnote_id: LN-7K3M9QX2`), and the QR icon at the top of the note shows its QR code. Print a workflow note's unit operations as **experiment worksheets** with a QR code on every page, write on them, then put phone photos or scanner output (images, PDF, zip) in a **PC scan folder** (Google Drive, KakaoTalk downloads, the scanner's folder…) or drop them on a window: the QR code is read and the image is filed in a `#### Worksheet scans` section at the end of that unit operation (compressed into the experiment's `images/scans/`, with a source caption, the same photo only once). The results window undoes each page, and pages that could not be read are assigned by hand. Sending them to your own Slack bot by DM works too (optional). See the [printout scan guide](docs/SCAN.md) (Korean).
- **LLM assistance (optional)**: Draft methods, summarize results, and extract samples via Ollama or OpenAI. The *Ask assistant* command lets the model call Labnote's own tools to reach a goal, confirming before any write (replacing a section shows the lines it removes and adds). Its final answer is shown in a dialog and goes into the note only when you press `Insert into note`. The end notice counts what it changed, looked up, had denied, and saw fail, and says so when nothing in the vault changed. When the model ends without an answer (including a thinking model that only thinks), every AI command says so. The same tools are available to external MCP clients.
- **Research automation (optional)**: One command scaffolds GitHub Actions, zero-dependency scripts, and AI-agent rules (`AGENTS.md`) into your vault to validate notes, open Experiment ↔ Issue links, and draft a Living-Manuscript Wiki — all opt-in and human-reviewed. See [Research automation](#research-automation).

## Requirements

- Obsidian `1.5.0` or later (latest version recommended).
- For the GitHub automation: [git](https://git-scm.com/downloads) and a GitHub account. (Not needed if you only take notes.)
- Node.js `22+` for development.

## Installation

Follow these steps top to bottom. Steps 1–5 are enough to start taking notes; steps 6–8 are only needed for the GitHub automation.

**Prerequisites (for automation)** — install **git** and create a **GitHub account** first. On Windows, install [Git for Windows](https://git-scm.com/download/win); it also enables Claude Code's Bash tool. Verify with `git --version`.

1. **Install Obsidian** from [obsidian.md/download](https://obsidian.md/download) (Windows/macOS/Linux).
2. **Create a vault** — a single folder is your vault. This folder later becomes your Git repository, so put it somewhere you control.
3. **Turn on community plugins** — Settings → Community plugins → **Turn on community plugins** (this turns off Restricted Mode).
4. **Install Labnote Assistant via BRAT** (it is not in the community directory yet):
   1. In **Browse**, search for `BRAT`, install **Obsidian42 - BRAT** (by TfTHacker), and enable it.
   2. Run **`BRAT: Plugins: Add a beta plugin for testing (with or without version)`** from the command palette — searching `beta plugin` finds it (older BRAT shows it as `BRAT: Add a beta plugin for testing`).
   3. Enter `sblabkribb/labnoteo`, leave the version at **Latest version** with **Enable after installing the plugin** checked, and click **Add Plugin**.
   4. If needed, refresh Settings → Community plugins and confirm **Labnote Assistant** is enabled.
5. **Verify** — run **`Create experiment`** from the command palette; a note opens. That is all you need for note-taking. Run **`Open user guide`** for the researcher quick start.
6. **(Automation) Run `Setup research automation`** — it writes `.labnoteo/`, `.github/`, `.gitignore`, `AGENTS.md`, `CLAUDE.md`, `QUICKSTART.md`, and `wiki-staging/` into the vault.
7. **(Automation) Connect an AI agent (Copilot)** — after step 6 so `AGENTS.md` exists. The simplest path on Windows is opencode, which Copilot downloads and manages for you. Do this before step 8 to let the agent make the first commit. See the **[Copilot agents guide](docs/COPILOT.md)** (Korean). Skip it if you only use manual git.
8. **(Automation) Create the repository and push** — after step 6 so `.gitignore` exists first:
   1. Create an **empty private** repository at [github.com/new](https://github.com/new) — do **not** add a README, `.gitignore`, or license, or the first push will be rejected. Copy its HTTPS URL.
   2. **Path A (recommended):** tell the connected agent, e.g. *"Initialize this folder as a git repo, set the hook, then commit everything and push to `<URL>`."* It follows `AGENTS.md` (sets `core.hooksPath`, no `--no-verify`).
   3. **Path B (manual git):**

      ```sh
      git init
      git config core.hooksPath .labnoteo/hooks   # enable the pre-commit hook BEFORE the first commit
      # macOS/Linux only: chmod +x .labnoteo/hooks/pre-commit
      git add .
      git commit -m "chore: initial vault"
      git remote add origin https://github.com/<user>/<repo>.git
      git branch -M main
      git push -u origin main
      ```

   Both paths may pop up a GitHub sign-in (Git Credential Manager) on the first push — that is normal.

**Why this order** — `.gitignore` (step 6) must precede the first push (step 8): once oversized raw data lands in Git history, nothing short of a history rewrite takes it back. The hook must be enabled before the first commit for the same reason, and the agent (step 7) connects after `AGENTS.md` exists but before the first commit so it can make that commit.

2. Create `.obsidian/plugins/labnoteo/` inside your vault and copy the three files into it.

The changes are listed and applied after you confirm; items the lab deleted are not brought back. When a plugin update changes the bundled catalogs, you are told once on startup. In a team, one person runs it and commits |
| Export tables to CSV | Export note tables to `<note name>.labnote_tableN.csv` next to the note. Bold, italic and code marks are dropped, and struck-through text is dropped with its marks (`~~0.10~~ 0.12` → `0.12`). A cell starting with `=` or `@`, or with a `+`/`-` that is not part of a number, gets a leading tab so Excel shows it as typed instead of evaluating it (numbers like `-80` are left alone). In a column where such a cell appears, like `+/-`, a lone `+` or `-` gets the tab too. Tables inside callouts and quotes (`> | … |`) are exported; tables inside code blocks (including code indented four spaces after a blank line — a table indented under a list item still counts) are skipped. The completion notice counts the files written and the ones left unchanged separately and shows the folder and file names (with a hint that the file explorer hides them while Obsidian's "Show all file types" setting is off). > A command that inserts at the cursor (Insert unit operation, Insert sample list of this experiment, a sample reference, AI drafts and summaries, …) run on a note in reading view switches it to editing view first, inserts near the end of the note, and says so (a unit operation goes after the last block). When a sample's alias or type changes, a note open only in reading view is fixed in its file and its view is left as it is.

> Renaming a workflow file in the file explorer automatically reorders the README checklist to match the new number prefix; deleting one removes its checklist entry (samples are kept — only that note's usage record is dropped), and its leftover `.labnote_tableN.csv` files are moved to the trash after asking. If a rename breaks the `###_….labnote.md` format, you are warned and offered a fixed name; once the format is back (by accepting the offer or fixing it by hand), the checklist follows the file again. A workflow moved into another experiment folder is not listed automatically — you get a notice; run `Sync workflow checklist with folder` there. If the moved note uses Local samples of its old experiment, you are asked whether to bring them into the new experiment's registry (copied if other notes in the old experiment still use them, moved otherwise). Moving one into a subfolder of its experiment (`images/` …) or out of the experiment warns that it is no longer a workflow step, and `Sync workflow checklist with folder` moves it back after asking. Aliases may contain brackets such as `[re]` (the checklist link writes them as `\[re\]`). A renamed note takes its `_tableN.csv` files along, an entry whose label matched the old file name follows the new name, and so do the note's `title` and `## [ID name]` heading if they matched it (labels and titles you edited by hand are kept). `Sync workflow checklist with folder` finds note titles/headings and labels that no longer match their file names and fixes them after asking. A "Make a copy" duplicate (`….labnote 1.md`) asks for the copy's own alias in a box prefilled with the original's, then gives it the next number and updates its file name, note `title`, and `## [ID name]` heading together before listing it (cancelling leaves the name, title, and checklist as they are). The copy's dates are reset then too (created and last updated today; `end_date` and the unit operations' `Start_date`/`End_date` emptied), as they are when you rename a copy into the format by hand; then the note's `title` and `## [ID name]` heading follow the new file name before you are asked to list it (so they match even if you decline). Moving a note to another folder takes its `_tableN.csv` files along and says so (a CSV whose name is taken there stays, with a warning). The copy's `@issue` markers get new IDs before that box opens, so they do not merge with the original's issues. `Insert workflow` (README right-click) creates a new workflow from the catalog.
>
> Experiment folder names must start with `###_` (e.g. `020_GFP`). If a rename drops the number, you are warned and offered the name with the old number back. Running a workflow command from a note in an unnumbered folder says the folder is not an experiment folder. Experiment folders must sit directly under `labnote/`; moving one into a subfolder such as `labnote/group/020_GFP` warns and offers to move it back under `labnote/`.
>
> When a note moved to another experiment uses Local samples that other notes of its old experiment still use (so they would be copied), you choose between bringing copies and moving those samples to Global while bringing the rest. Renaming or renumbering notes updates the usage record (`sources`) in the Local registry to the new names.

## Research automation

Beyond the notebook itself, labnoteo can turn your vault into a lightweight research-notes system on GitHub — note validation, Experiment ↔ Issue links, and a Living-Manuscript Wiki — without you writing any CI by hand. Run **Setup research automation** from the command palette to provision these assets into the current vault.

- **Large-file protection** — `check-large-files.mjs` + a pre-commit hook + `.gitignore` block oversized data before commit.
- **Validation** — `validate.mjs` + `validate.yml` check `status` values, duplicate experiment ids, duplicate note IDs (`labnote_id`), and `@issue` marker format with folder-unique ids on every push.
- **Experiment ↔ Issue** — `issue-sync.mjs` + `experiment-issues.yml` open one thread Issue per `discuss: true`/`status: needs-review` experiment, plus one Issue per `@issue` marker across all `*.labnote.md` in the folder. Deterministic and idempotent.
- **AI agent rules** — `AGENTS.md`/`CLAUDE.md` govern a local AI agent's git, commit, Issue-signal, and Wiki-draft behavior.
- **Living-Manuscript Wiki (optional)** — `wiki-sync.yml` publishes human-reviewed `wiki-staging/` drafts to the GitHub Wiki.

The bundled scripts are **zero-dependency** Node ESM, so no `npm install` is needed in the vault. All server-side automation is **deterministic** (GitHub-hosted runners, no server-side LLM); AI judgments are made by a **local AI agent** following `AGENTS.md`, while issue creation and Wiki publishing stay solely with the server, so nothing is duplicated. Automation **never rewrites your notes**; `status` changes and scientific judgment stay with you.

**Updates** — after a plugin update, Obsidian brings the installed files up to the new version when it starts. Files you have not edited since they were installed (the `.labnoteo/` scripts and `SETUP.md`, the `.github/` workflows, …) are replaced, `AGENTS.md` and `QUICKSTART.md` get only their managed block (`<!-- BEGIN labnoteo (managed) -->` to `END`) refreshed (a block you edited is not replaced automatically but listed, and running *Setup research automation* again asks before replacing it), and `.gitignore`/`CLAUDE.md` only gain missing lines; you are told which files changed. Files you edited, and files missing from the vault, are left alone and only listed (once per new version), so run *Setup research automation* again then. `wiki-staging/` drafts are never changed automatically. Which template each file was matched to is recorded in `.labnoteo/installed.json`; commit it along with the rest. In a vault without that record (set up before 0.95.0), files still exactly as an earlier version wrote them, and the `.labnoteo/scripts/*.mjs` bundles, are updated automatically as well. Server-side behavior changes only once the updated files are committed and pushed.

Your lab's own rules in `QUICKSTART.md` survive updates when written **below** the managed block. A `QUICKSTART.md` created before 0.99.0 is switched to this form on startup if you never edited it; an edited one is only listed, and running *Setup research automation* again switches it after you confirm (the edits are lost then, so copy them out first).

**Attachment location** — after *Setup research automation*, if Obsidian's default location for new attachments is still the vault root, you are asked whether to switch it to `./images` (an images folder next to the note, which for a lab note is the experiment's `images/`). It is the same as changing Obsidian's Settings → Files and links → Default location for new attachments.

See the generated `.labnoteo/SETUP.md` (admins) for the full asset table, prerequisites, and backfill procedure, and `QUICKSTART.md` (researchers) for day-to-day usage. `AGENTS.md` is [shared with Copilot](docs/COPILOT.md).

## Settings

**Samples** — **Sample tracking** turns autocomplete, highlighting and `{Type}.json` registry sync on or off (reload to apply); `sample_tracking: 'no'` in an experiment README's front matter turns them off for that experiment's notes only (the Samples view, MCP and AI tools follow the setting alone). Add custom sample types, and set the **Global sample folder** (default `resources/labsamples`). Custom types may be Korean (`배지` gets `@배지` autocomplete and highlighting); use letters, digits and `_` only — a type with a space or `-` (`Cell Line`, `Cell-Line`) is not autocompleted, so the field does not save it and suggests a name such as `Cell_Line` (a name saved by an earlier version is kept, with a warning). A name that differs from a built-in or an earlier type only in letter case (`dna`, or `strain` next to `Strain`) is not saved either: on Windows both types would share one `{Type}.json` and their samples would mix. Editing the field updates the Samples view right away, and closing settings after removing a type that still has samples says those samples will no longer show and offers to put the type back. A sample created from a note at the vault root becomes a global sample whatever experiment you opened before, since that note's local folder is the global one, and you are told so (the Samples view's Local section says so too). After you change the folder and close settings, you are asked whether to move the samples left in the old folder to the new one; a sample whose ID the new folder already has, and a catalog file of the same name, stay put with a notice.

**Workflows** — **Auto-sync unit operation TOC** reorders a workflow note's `Related Unit Operations` list to match heading order after edits, so moving a unit-operation block re-sorts the top-of-note TOC. Dragging a block in Obsidian's Outline view tidies the TOC and `---` separators right away, and dropping it onto another unit operation places it after that whole unit operation instead of splitting it. The cleanup is saved separately from the move, so undoing back to before the move may take two presses of Ctrl+Z. Deleting or cutting a whole unit-operation block in the editor drops its TOC entry in the same undo step, so one Ctrl+Z brings back both. The TOC links follow GitHub's anchor rules (non-ASCII text kept, a repeated unit operation numbered `-1`, `-2`) so they jump to the right block when the note is viewed on GitHub; inside Obsidian, click the Outline view instead of the TOC links. On by default. **Auto-update last updated date** sets a lab note's (`*.labnote.md` in an experiment folder) front matter `last_updated_date` to today (Asia/Seoul) when you edit it in the editor, change it with `Change experiment status` or `Toggle discussion flag`, or the AI edits it. Each note changes at most once a day, and editing a workflow note also updates its experiment README, as does creating a workflow. Changes pulled with git and undo are ignored, and automatic tidying such as the checklist sync or renumbering does not change the date. A note whose date you edit by hand keeps that date for the rest of the day (with a one-time notice) and is stamped again from the next day; turning the setting off and on resumes it at once. The date update is itself an undo step, so undoing the day's first edit may take one more Ctrl+Z. On by default.

**Barcode & scans** — **Worksheet paper size** (A4 or Letter, also changeable in the print window). **Scan folder** and **Scan folder mode** (desktop only): the PC folder photos and scans arrive in, and how it is treated — a **Dedicated folder** has handled originals moved to `labnote-processed/` or `labnote-failed/`, a **Shared folder** keeps originals and passes over files without a worksheet QR code. It is checked at startup and every 30 seconds, and only files added after it was set are read (**Process existing files too** is a separate button). These values do not sync with the vault's settings; they are kept per PC and per vault, so set the folder on one PC only. **Unmatched scans** shows how many pages wait to be assigned, with an **Assign unmatched scans** button. **Stored scan size** and **Stored scan quality** set the long edge (default 2400 px) and JPEG quality (default 85%) of stored scans. **Scan width in notes**: scans filed into notes show as thumbnails (default 200 px) with an **Open full size** link after the caption; 0 shows them full size, and scans already filed keep their size. **Slack scans (optional)**: enter the **Slack bot token** and **Where you send scans** (direct message to the bot or a private channel) and press **Connect** — the token, its permissions and the channel invite are checked right away. Send the link code to the bot; files that user sends are then filed about every 90 seconds (incoming messages get an 👀 reaction), with results replied in the thread. The token stays on this PC; link only one PC. See the [printout scan guide](docs/SCAN.md) (Korean) for each way in. `_labnote-scans/` (the unmatched queue) is excluded from commits by the research automation's `.gitignore`; an existing vault picks this up when *Setup research automation* is run again after the plugin update.

**AI provider** — pick `none`, `ollama`, or `openai`; set the Ollama/OpenAI endpoint (separate fields so an OpenAI key never leaks to a local Ollama address; written without `http://` or `https://`, as in `localhost:11434`, it gets `http://` when connecting), the model id (e.g. `qwen3`, `gpt-4o-mini`), and the API key (OpenAI-compatible only, never sent to Ollama).

When an AI request fails, the notice names the cause and the setting to fix: the endpoint when the server cannot be reached, the API key on 401/403, the model when it is not found, and the endpoint path (server address only, without `/v1` or `/api`) on any other 404; an endpoint that is not an `http://` or `https://` address (a typo such as `htp://`) gets told how to write it. The original error stays in the developer console (Ctrl+Shift+I, or Cmd+Option+I on macOS).

> **Tool calling needs a model with function-calling support.** With Ollama, pick a model that advertises the `tools` capability (`qwen3`, `llama3.1`, …); one without it answers in prose instead.

**MCP server & Copilot agents** — to expose Labnote's tools to an external MCP client, or to hand commits/Issues/Wiki drafts to Copilot's agent mode, see the **[Copilot agents guide](docs/COPILOT.md)** (Korean).

## Development

This is an npm workspaces monorepo:

- `src/` — the Obsidian plugin, bundled to `main.js` at the repository root via esbuild. The plugin lives at the root because Obsidian's community directory reads `manifest.json` from there.
- `packages/labnoteo-core` — platform-neutral core logic (parsers, workflow/sample domain), consumed by the plugin. It must not import Node-only APIs; anything platform-specific goes behind a port (`LabnoteFs`, `LabnoteHost`).
- `automation/` — sources for the vault-scaffolded [Research automation](#research-automation) scripts. esbuild builds them (Stage 1) to zero-dependency `dist-automation/*.mjs` — reusing the same `@labnoteo/core` source as the plugin, so there is no drift — and embeds them (plus the workflow/AGENTS.md/Wiki templates) as strings inside `main.js` (Stage 2). This keeps a 3-file install self-sufficient; the *Setup research automation* command writes those strings out into the vault. Not every source here ships: `issue-gate.ts` and `wiki-propose.ts` are excluded from the build, since the local AI agent makes those judgments now (see `esbuild.config.mjs`); they are kept as sources for a possible opt-in path.
- `issue-sync` and `validate` must see the *same* markers, so both read a folder through `readMarkerSources` rather than reading a README directly — narrowing either one alone would mean opening issues for markers that were never validated, or the reverse.
- `tests/` — plugin-layer tests, plus a runtime stub for the `obsidian` package (which ships types only). Core tests live beside the code in `packages/labnoteo-core/src/__tests__/`.

```bash
npm install           # install all workspaces
npm run dev           # watch build
npm run build         # bundle the Obsidian plugin -> main.js
npm run typecheck     # typecheck core + plugin
npm test              # run all tests (vitest: core + plugin projects)
npm run sync:versions # propagate root version to packages, manifest, and READMEs
```

`npm run sync:versions -- --check` writes nothing and fails if any target has drifted from the root `package.json` version; CI runs it that way.

Every `LabnoteFs` implementation must pass the shared contract in `packages/labnoteo-core/src/__tests__/labnoteFsContract.ts`, which is where the atomicity guarantee behind `{Type}.json` is enforced.

`npm run record:fixtures` re-records the LLM response fixtures in `tests/fixtures/llm/` against a live provider — see that folder's README for why they exist and how to read their provenance.
